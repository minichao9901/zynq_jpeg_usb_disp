# 实体 LCD 反复黑屏/亮屏修复

2026-11-06，Asia/Shanghai。实体屏为 800×480，读回 LCD ID=0x4384。

## 现象与定位

用户接屏实测后，副屏反复黑屏、亮屏，看起来像画面重新启动，而非普通撕裂。
旧实现仅做过未接屏的 USB、解码及物理 DDR 校验，不能代表 LCD 连续视频输出正确。

故障状态采样 5 秒：frames 4577→4784，USB resets 始终 1、session 始终 2，bad、display_errors、rx_timeouts 都为 0。
这段窗口没有观察到 USB/程序重启。仅停止更新后，屏幕停在黑屏；重新初始化并只输出开机色条时，用户确认色条稳定。
开始动态更新才黑闪，定位到旧 `display_commit()` 每帧 `DmaStop`→改地址→`DmaStart` 的实现。
该操作打断了连续 AXI4-Stream 视频。视频输出重新锁定是黑屏循环的机制推断，未用示波器直接采集内部 locked/underflow 信号。

## 修复

- VDMA 只在初始化时启动一次，运行中不为换图停 MM2S、不重启 VTC/像素时钟。
- 按 AMD [PG020 Programming Sequence](https://docs.amd.com/r/en-US/pg020_axi_vdma/Programming-Sequence)，
  新地址通过 START_ADDRESS 写入，最后写 VSIZE 提交影子参数，在帧边界生效，RS 持续为 1。
- 使用五个软件帧缓冲：当前已编程帧、最多两代延迟回收读者、待发布帧、CPU 绘制帧。
- 地址替换后，旧缓冲等待至少两个观测到的完成事件才复用。完成标志可能合并，漏计只会推迟回收，不会提前释放。
- 仅在观测到帧完成事件时发布最新完整帧。输入快于显示时替换旧待发布帧，保持 USB 接收与解码不人为限速。
- JPEG 解码错误会释放绘制槽，但不破坏上一幅完整待发布或正在扫描的画面。
- 矩形更新从最新完整合成画面复制，保留区域外内容；不会在扫描帧上直接绘制。
- 更新 CLI：除 USB 配置/帧类型/构建身份，还检查持续扫描能力、RS、帧事件及真实地址发布。
  没有声明持续扫描的旧产物会在下载前被拒绝。

两个模式共用此显示路径，分别重编译 RGB/JPEG ELF；PL bit 内容不变。

## 诊断与验证

新增 vendor IN 0x35（bmRequestType=0xC1，wIndex=1，128字节），字段顺序见 `tools/usb_host.py` 的 DISPLAY_KEYS。
包括 programmed/latest/ready/drawing 地址、旧缓冲保护掩码、decoded/published/replaced、帧完成事件、RS 和错误观测。

`frames/decoded` 表示收到并处理的完整帧；`published` 表示交给硬件帧边界更新的画面数。
二者不再混同于面板实际显示帧数。`replaced` 增加是保留最新完整帧策略，不是 USB 包丢失。
`wait_display()` 用于测试停止发送后等待最终画面发布并跨过保护边界，再做物理 DDR 比较。

用户在加载持续扫描版本后，拖动窗口/动态内容观察结果为：**“已经稳定，不再黑闪”**。
连续遥测中 RS 保持 1、帧完成事件持续前进，halted_seen、error_seen、no_buffer 都为 0。
JPEG 五类整图、矩形、损坏/截断恢复测试及 RGB 九项回归通过，物理 DDR 图像比较通过。

有效 RGB 三轮正常路径为 41.611 / 41.726 / 41.706 MB/s，中位 **41.706 MB/s**；纯接收中位 **41.841 MB/s**。
这些是解码处理/接收能力；待发布帧被替换时，不把收到的全部帧数当作面板显示帧数。

另一次 RGB 吞吐测试过程中，用户手动重新下载了 JPEG，导致 USB pipe error 和桌面恢复失败。
用户已确认该操作；中断结果不作为性能结论，之后在板子独占验证期间重新完成了上述有效测试。
当前接屏验证证据保存于 `docs/validation/lcd-continuous-20261106/`。
